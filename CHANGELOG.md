## [v15.15] — 2026-05-10

### Добавлено

- **Расширенные метрики бэктеста: Naïve baseline, R² на доходностях, IC** —
  три взаимосвязанных улучшения, закрывающих главный академический риск проекта:
  высокий R² (≈ 0.80) на ценах тривиален из-за трендовости ряда и сам по себе
  не является доказательством полезности модели.

  **1. Naïve baseline** (`naive_price = last known close`):
  - Для каждого горизонта показывается ошибка тривиального предсказания «цена
    не изменится» — самый сильный контраргумент на защите.
  - Итог: `Naive Error: X RUB (Y%) | модель лучше/хуже Naive`.
  - На горизонтах 1–2 дня модель стабильно бьёт Naïve; на горизонте 3 дней
    Naïve конкурентоспособен — это честно показывает пределы модели.

  **2. R² на дневных доходностях** (`r2_score` по трём горизонтам):
  - Доходность = `(price_h - base_price) / base_price * 100`.
  - R² на доходностях типично отрицательный или близкий к нулю (в отличие от
    R² ≈ 0.80 на ценах) — именно это и является честной мерой прогнозного
    качества на финансовых рядах. Значение выводится с явной пометкой числа
    горизонтов (`на 3 горизонтах`) для прозрачности оценки.

  **3. IC (Information Coefficient, Spearman)** — корреляция ранков
  предсказанных и фактических доходностей по горизонтам:
  - Стандартная метрика количественных фондов (IC > 0.05 значимо,
    IC > 0.10 — сильный сигнал).
  - На 3 точках принимает дискретные значения; стабилизируется при
    расширенном бэктесте (10+ дат).
  - Вычисляется через `pd.Series.corr(method='spearman')` без новых
    зависимостей.

  **Изменения в `stock_modelv15.py`** (`run_backtest` + блок вывода):
  - В словарь `backtest_results` добавлены поля:
    `naive_price`, `naive_error`, `naive_error_pct`,
    `model_return_pct`, `real_return_pct`.
  - Per-horizon вывод: строка `Return: model X% | real Y%`.
  - AVERAGE METRICS: `Naive Error`, `R2 on returns`, `IC (Spearman)`.
  - Лог-файл бэктеста: аналогичное обновление.

## [v15.14] — 2026-05-10

### Добавлено

- **Миграция LSTM с TensorFlow/Keras на PyTorch** — TF ≥2.10 не поддерживает CUDA на
  Windows нативно; LSTM-обучение шло на CPU и занимало ~80% времени прогона. PyTorch
  поддерживает Windows CUDA через `cu128` wheel (RTX 50 Blackwell, sm_120).

  Изменения в `stock_modelv15.py` (~200 строк):
  - Класс `LSTMRegressor(nn.Module)` — точный аналог Keras-архитектуры (3 LSTM-слоя
    с decreasing dropout + Dense(32) + Dense(1))
  - `train_lstm_torch(model, X, y, lr, epochs, patience, batch_size)` — manual
    EarlyStopping с `restore_best_weights` (хранит `state_dict` лучшей эпохи и
    восстанавливает после прерывания), `validation_split=0.2` на хвосте
  - `predict_lstm_torch(model, X)` — eval mode + `torch.no_grad()`, возвращает 1D numpy
  - `optimize_lstm_params` использует 2-слойный `_OptunaLSTM` для быстрого trial
    (как было в Keras-версии)
  - `tf.random.set_seed` → `torch.manual_seed + cuda.manual_seed_all`
  - 3 места `_m.predict(verbose=0)` → `predict_lstm_torch(_m, X)`
  - Глобальная константа `TORCH_DEVICE = torch.device('cuda' if available else 'cpu')`

  Кросс-тикерный замер (5 тикеров × 3 горизонта):

  | Тикер | h | Keras CPU R² | PyTorch GPU R² | ΔR² | LSTM_coef |
  | --- | --- | --- | --- | --- | --- |
  | SBER | 1 | 0.887 | 0.888 | +0.002 | 0.388 |
  | SBER | 3 | 0.772 | 0.781 | +0.010 | 0.000 |
  | LKOH | 1 | 0.832 | 0.820 | -0.012 | 0.082→**0.267** |
  | GAZP | 1 | 0.793 | 0.796 | +0.003 | 0.202→0.172 |
  | TCSG | 1 | 0.659 | **0.698** | +0.039 | 0.000 |
  | TCSG | 3 | 0.373 | **0.416** | +0.043 | 0.000 |
  | YDEX | 1 | 0.604 | **0.641** | +0.037 | 0.000→**0.266** ✓ |
  | YDEX | 2 | 0.362 | **0.405** | +0.043 | 0.000→**0.174** ✓ |
  | YDEX | 3 | 0.396 | **0.421** | +0.025 | 0.000→**0.181** ✓ |

  - Среднее R²: 0.654 → 0.665 (+1.1 pp)
  - Ненулевых LSTM_coef: 6/15 → 8/15 (YDEX все 3 горизонта ожили)
  - Время полного прогона 5 тикеров: ~1h45min → **~25 min (×4)**
  - На один LSTM seed: ~25 sec (Keras CPU) → ~5 sec (PyTorch GPU) = **×5**

- **Защитная валидация размера данных перед walk-forward** — на коротких рядах
  (`len(X) < 200` sequences) последний test-сет получался <10 семплов, метрики
  становились бессмысленными. Реальный пример (TCSG до v15.13): 1187 sequences,
  test=59, R²=-1.0. Введены два порога:
  - `_MIN_SEQUENCES_HARD = 200` → error + `return None` (caller обрабатывает через
    `merge_horizon_results`, который уже умел с `None`)
  - `_MIN_SEQUENCES_WARN = 500` → warning об ожидаемой нестабильности OOS

- **GPU memory cleanup после walk-forward** — на каждый горизонт
  `prepare_and_train_model()` создаёт 9 LSTM-моделей (3 splits × 3 seeds), но для
  финального прогноза нужен только `models[-1]`. Без очистки на h=1/h=2/h=3 копилось
  до 27 LSTM-тензоров в VRAM. Решение: после цикла обнулить ссылки на LSTM в
  `models[:-1]` и вызвать `torch.cuda.empty_cache()`.

### Изменено

- `requirements.txt`: `tensorflow==2.20.0` → `torch==2.11.0+cu128`
- Установка torch: `pip install torch --index-url https://download.pytorch.org/whl/cu128` (~2.8 GB)
- В стартовом логе: `TensorFlow: 2.20.0` / `GPU Available: []` → `PyTorch: 2.11.0+cu128`
  / `GPU Available: NVIDIA GeForce RTX 5070 Ti (CUDA 12.8)`

### Воспроизводимость

PyTorch и TF дают разные числа для одного seed (разная инициализация весов, разный RNG).
На SBER с теми же сохранёнными hyperparams (`units=67`, `dropout=0.227`, `lr=0.008`)
PyTorch стабильно даёт **чуть лучшие** OOS-метрики (+0.002...+0.043 R²), что
объясняется отсутствием Keras-overhead и более точным GPU-вычислением gradient.

### Ремарка

Для полной переоптимизации hyperparams под PyTorch-архитектуру нужно перезапустить
`--optimize --trials 30` для каждого тикера (записано в `improvements.md`).

## [v15.13] — 2026-05-10

### Добавлено

- **TCSG/T автоматический переход на новый тикер** — TCS Group Holding PLC (тикер
  `TCSG`) был реструктурирован в МКПАО «Т-Технологии» (тикер MOEX: `T`) в ноябре 2024
  после смены юрисдикции (Кипр → РФ). MOEX делистнул TCSG; модель училась на
  стейл-данных с 2024-11-27, R² катастрофический (h=1=0.014, h=2=−0.31, h=3=−1.00).

  **Ключевая особенность:** MOEX отдаёт под тикером `T` уже **склеенную историю**
  TCSG+T (1697 строк, 2019-10-28 → сегодня), отдельный concat не нужен (в отличие
  от YDEX, где YNDX и YDEX раздельны). Решение: использовать `T` endpoint и
  проставить дамми `is_post_restructure` по дате.

  В `load_stock_data_moex_test`:

  ```python
  if ticker_symbol in ('T', 'TCSG'):
      data = _load_single_ticker('T', start_date, end_date)
      if data is None or data.empty:
          data = _load_single_ticker('TCSG', start_date, end_date)
      data['is_post_restructure'] = (data['Date'] >= pd.to_datetime('2024-11-28')).astype(int)
      return data
  ```

  Принимаются оба имени тикера (`--ticker TCSG` и `--ticker T`) — оба возвращают
  единую серию.

### Эффект на метрики

| h | R² было (stale TCSG) | R² стало (TCSG+T) | Δ |
| --- | --- | --- | --- |
| 1 | 0.014 | **0.659** | **+64.5pp** |
| 2 | -0.31 | **0.509** | **+82pp** |
| 3 | -1.00 | **0.373** | **+137pp** |

Среднее R²: -0.43 → +0.514 (+95pp). TCSG/T теперь работает на уровне SBER/LKOH/GAZP.
LSTM_coef везде 0.000 — ожидаемо: T-эпоха короткая (449 дней), LSTM не может выучить
устойчивых паттернов на короткой подвыборке со structural shock.

### Урок (отдельный коммит-эксперимент)

Первая попытка делать `concat(_load_single_ticker('TCSG'), _load_single_ticker('T'))`
дала мусор — `T` endpoint уже включает TCSG период, после `concat + drop_duplicates`
получалось 621/1076 вместо 1248/449 (нестабильный sort внутри одной даты), R²=-22.74.
После диагностики (raw query на оба endpoint-а) обнаружено что MOEX делает склейку
сам — реализация упрощена до прямого использования `T` + дамми по дате.

  диагностику v15.10): LSTM и XGB получали один и тот же набор ~39 фич; XGB на

- В forecast: отдельный `_lstm_input` для последнего окна

## [v15.10] — 2026-05-10

### Добавлено

- **`Ridge(positive=True)` — запрет отрицательных весов в мета-леарнере** — корень
  проблемы: `optimize_ridge_alpha` искал `alpha ∈ [1e-3, 100]`, нижняя граница 1e-3
  даёт почти OLS. LSTM и XGB сильно скоррелированы (мультиколлинеарность —
  обе предсказывают Close), при слабой регуляризации Ridge находит «трюк»: инвертирует
  LSTM (LSTM=-0.136) и амплифицирует XGB (XGB=1.128) ради минимально лучшего MSE на
  CV — подгонка к шуму, не реальный сигнал.

  `positive=True` применён в трёх местах:
  - `optimize_ridge_alpha` (внутри Optuna objective)
  - per-fold `meta_learner` (`alpha=1.0`)
  - финальный retrained `best_meta`

  Эффект на SBER: на h=1 LSTM получает честный вес 0.350 (полезен), на h=2/h=3 Ridge
  сам обнуляет LSTM (0.000) — модель сводится к чистому XGB, без артефактной инверсии.

- **LSTM EPOCHS 10→100, PATIENCE 3→10** — корень: 10 эпох катастрофически мало,
  модель не успевала обучиться, `restore_best_weights=True` с `patience=3` оставлял
  почти untrained model. Замер на SBER (EPOCHS=100): train loss упал ~вдвое
  (0.0014 → 0.0008), per-fold LSTM_coef вырос с avg 0.276 до 0.317 (+15%). Финальный
  OOS LSTM_coef на h=1: 0.350 → 0.400 (+14%), на h=2/h=3 без изменений (LSTM не
  обобщает на длинных горизонтах — это адресовано в v15.11).

  PATIENCE=15 давал переобучение на части seeds (val/train gap 4-9×), `PATIENCE=10`
  здоровый компромисс.

- **Умное сообщение Ljung-Box** — старая логика: всегда «автокорреляция обнаружена»
  при p<0.05, что вызывает ложную тревогу. Новая логика различает три случая:
  - **ARCH-эффект** (длинные лаги ≥5 + p<0.05 в `|res|`): «норма для фин. рядов;
    CI постоянной ширины» — гетероскедастичность, не баг
  - **momentum в среднем** (lag 1-3): «структура не учтена» — можно добавить AR
  - **длинная структура** (lag 4+ без `|res|`): «макро-лаг»

  Дополнительно: топ-3 худших лагов, LB на `|res|` (proxy для ARCH-теста), per-fold
  LB (артефакт склейки vs реальное свойство). Для SBER на всех горизонтах: лаги 18–20
  плюс heteroscedasticity → ARCH; корень — гетероскедастичность, не бага модели.

- **SSL retry + verify=False fallback в загрузчике котировок** — `UNEXPECTED_EOF_WHILE_READING`
  — транзиентная SSL-ошибка (обрыв TLS-сессии), повторная попытка обычно помогает.
  Реализация:
  - moexalgo: 3 попытки с экспоненциальным backoff (1s, 2s)
  - Direct MOEX ISS: 3 ретрая на каждую страницу пагинации; при SSL-ошибке повтор
    с `verify=False` как последний резерв
  - Логика: пустой тикер → сразу `break`, не пробуем оба SSL-режима

### Открыто (записано в improvements.md)

- **GARCH-CI (адаптивные доверительные интервалы)** — диагностика v15.10 подтвердила
  ARCH-эффект; идея: вместо квантильных XGBoost на residuals — модель волатильности
  (GARCH(1,1) или EWMA на `|res|`), CI = forecast ± k·σ_t. Шире в кризисы, уже в
  штиле; решает гетероскедастичность напрямую. Хороший самостоятельный пункт диплома.

## [v15.9] — 2026-05-09

### Добавлено

- **Дивидендные time-varying признаки** — новый модуль `fundamentals_loader.py` с функцией
  `load_dividend_features(ticker, start, end)`. Работает для **любого тикера MOEX** через
  универсальный endpoint `iss.moex.com/iss/securities/{ticker}/dividends.json`.
  Возвращает три признака на каждый календарный день диапазона:

  | Признак | Значение | Sentinel |
  | --- | --- | --- |
  | `div_days_to_next` | Дней до следующей даты закрытия реестра | 999 — дивиденд не объявлён |
  | `div_next_amount` | Объявленный дивиденд на акцию (руб.) | 0.0 — дивиденд не объявлён |
  | `div_days_since_last` | Дней с последнего закрытия реестра | 999 — до первой выплаты |

- **Константа `_FUND_DIV_COLS`** — список из трёх дивидендных колонок, аналогичный `_MACRO_COLS`;
  используется при формировании feature vector и в Granger-скрининге.

### Механика look-ahead bias mitigation

Ключевая сложность дивидендных признаков — информация о будущем платеже не должна
просачиваться в признаки до того, как она была публично объявлена.

MOEX ISS возвращает только `registryclosedate` (дату закрытия реестра) и сумму дивиденда,
но **не дату объявления**. Для исключения look-ahead bias введено окно `_ANNOUNCE_WINDOW = 45`
дней: признак `div_days_to_next` ненулевой (< 999) только если до `registryclosedate` не
более 45 дней. Для SBER и большинства компаний MOEX дата закрытия реестра публикуется в
пресс-релизе Совета директоров за 2–4 недели, то есть 45-дневный порог с запасом покрывает
реальный срок объявления. Всё, что дальше 45 дней — считается неизвестным, признак = 999.

Признак `div_days_since_last` look-ahead bias не имеет: он всегда считается от прошедших дат.

### Механика ценового сигнала

Дивиденды создают два детерминированных паттерна в ценовом ряду:

1. **Дивидендный захват (pre-ex накопление)**: за 5–15 торговых дней до ex-dividend date
   (≈ `registryclosedate − 1 б.д.` при T+2-расчётах) цена растёт, так как инвесторы,
   рассчитывающие получить дивиденд, докупают акции.

2. **Ex-dividend гэп**: в день ex-дивиденды цена открывается ниже примерно на сумму дивиденда
   (для SBER 2024 — минус ≈33 руб., или ≈11% от цены). Гэп достаточно предсказуем, чтобы
   LSTM мог использовать `div_days_to_next` как сигнал-предвестник.

Поэтому `div_days_to_next` (обратный отсчёт 45→0) теоретически должен пройти Granger-скрининг:
изменение Close коррелирует с изменением этого счётчика в [−1, 0]-лаговом окне.

### Интеграция в пайплайн

- `fundamentals_loader.load_dividend_features(ticker, start, end)` вызывается **один раз**
  до цикла `for h in [1, 2, 3]` в блоках бэктеста и обычного прогноза;
  результат передаётся как `div_data=shared_div` в `prepare_and_train_model`.

## [v15.8] — 2026-05-09

### Добавлено

- **LSTM Ensemble по seeds (N=3)** — вместо одной LSTM-модели на каждый walk-forward сплит обучаются три независимые модели с разными seed инициализации весов: `ENSEMBLE_SEEDS = [42, 7, 123]`. Предсказания трёх моделей усредняются поэлементно (`np.mean(..., axis=0)`) до передачи в Ridge мета-леарнер — мета-леарнер по-прежнему получает два входных признака `[lstm_avg_pred, xgb_pred]` и не меняет свою размерность.

### Изменено

- **`ENSEMBLE_SEEDS = [42, 7, 123]`** — новая константа рядом с `RANDOM_SEED`; задаёт seeds для трёх LSTM в ансамбле. Для воспроизводимости перед каждым из трёх обучений вызываются `tf.random.set_seed(_seed)` и `np.random.seed(_seed)`; после цикла seed сбрасывается в `RANDOM_SEED`.

- **Хранение моделей** — `models.append(...)` теперь хранит список `[lstm_m1, lstm_m2, lstm_m3]` вместо одного `lstm_model`; распаковка `best_lstm_ensemble, best_xgb_model, best_meta_learner = models[-1]`.

- **Генерация прогноза** — `lstm_pred_scaled` вычисляется как среднее предсказаний всех трёх LSTM на последнем окне LOOK_BACK=30.

- **Логирование** — заголовок `"Training LSTM ensemble (3 seeds)..."`; после каждого seed выводятся `train_loss` и `val_loss` этой конкретной модели.

### Почему вариант A (усреднение до мета-леарнера)

Ridge получает по-прежнему два признака, что сохраняет интерпретируемость весов (coef_[0]=LSTM, coef_[1]=XGB). Альтернатива (Вариант B — 4 входа: три LSTM + XGB) потребовала бы переобучения Optuna Ridge alpha с новым числом фичей и усложнила бы диагностику.

### Ожидаемый эффект

Дисперсия avg Error% на SBER benchmark исторически составляла 0.55%–2.7% между прогонами при одном seed — из-за стохастической инициализации весов LSTM. Усреднение N=3 моделей теоретически снижает дисперсию в √3 ≈ 1.7 раза. Время прогона возрастает примерно в 3 раза по блоку LSTM.

- `prepare_and_train_model` — авторегрессивный прогноз на 2–3 дня заменён прямыми независимыми моделями на каждый горизонт (Direct Multi-Step Forecasting / MIMO):
  - Добавлен параметр `horizon: int = 1`
  - При подготовке обучающих последовательностей цель сдвигается: `y[i] = Close[i + horizon]`; верхняя граница цикла `len(scaled_df) - horizon`
  - Прогнозный блок: одно прямое предсказание из текущих данных вместо авторегрессивного цикла; синтетические строки Open/High/Low/Volume удалены

  - Итого моделей: 54 (18 на горизонт × 3) вместо 18

### Причина

Авторегрессивный подход накапливал ошибку: для прогноза на день 2 и 3 модель получала синтетические Open/High/Low/Volume, а технические индикаторы (RSI, ATR, Bollinger Bands и др.) пересчитывались на основе этих фиктивных значений. Ошибка дня 1 входила в признаки дня 2, ошибка дня 2 — в признаки дня 3. Доверительные интервалы для горизонтов 2 и 3 были статистически несостоятельны.

### Плюсы нового подхода

- Нет накопления ошибки — каждый горизонт предсказывается независимо из реальных данных
- Честные CI — квантильные модели каждого горизонта обучены на соответствующем сдвиге цели
- Академически обоснован: Direct Multi-Step / MIMO forecasting — стандарт для горизонтов > 1
- Интерпретируемые метрики: RMSE/MAE/R² отдельные для каждого горизонта (показывают деградацию качества с ростом горизонта)
- Внешний интерфейс (`forecasts[h][-1]`, `confidence_intervals[h]`) не изменился — код вывода не тронут

### Минусы / компромиссы

- Время обучения ×3 (54 модели вместо 18)
- Три независимых ансамбля без разделяемого представления между горизонтами
