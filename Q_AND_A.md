> коммитов. Включает положительные и **отрицательные** результаты.

## 0. Основы: что делает модель

### Q: Какие поля в выводе forecast и почему именно они?

**A**: После апгрейда (12.05.2026) forecast-вывод даёт **6 полей на каждый
горизонт**, каждое из которых отвечает на конкретный вопрос пользователя.

**Пример вывода**:

```text
FORECAST SUMMARY: SBER
Текущая цена: 322.00 RUB (12.05.2026)
========================================================================
+1d  13.05.2026   323.14 RUB  +0.35%  UP    [HIGH]
        CI: [321.54 - 326.12]  ширина 4.58
+2d  14.05.2026   319.37 RUB  -0.82%  DOWN  [MED]
        CI: [319.26 - 323.05]  ширина 3.78
+3d  15.05.2026   321.14 RUB  -0.27%  DOWN  [MED]
        CI: [313.60 - 321.61]  ширина 8.01

Naive baseline (без модели): 322.00 RUB для всех горизонтов
```

**Зачем каждое поле**:

| Поле | Отвечает на вопрос |
| --- | --- |
| **Дата** | Когда — учитывает торговый календарь (выходные пропускаются) |
| **Forecast (RUB)** | Точечная оценка цены закрытия |
| **Δ%** (`+0.35%`) | Сколько в % от текущей цены — понятнее, чем абсолютное число |
| **Direction** (UP/DOWN/FLAT) | **Куда** пойдёт цена — главный практический вопрос |
| **Confidence** (HIGH/MED/LOW) | Насколько модели можно доверять — основано на walk-forward R² |
| **CI** + ширина | Диапазон риска (5/95 или 25/75 в зависимости от `--ci-mode`) |

**Дополнительно в шапке**:

- **Текущая цена** + дата — точка отсчёта, без неё Δ% бессмысленна
- **Naïve baseline** в конце — напоминание, что было бы без модели

**Confidence-категории**:

- **HIGH**: R² ≥ 0.85 — модель уверена в этом горизонте
- **MED**: 0.70 ≤ R² < 0.85 — типичная зона для финансовых рядов
- **LOW**: R² < 0.70 — модель неуверена, к прогнозу относиться осторожно

**FLAT threshold**: Δ% в диапазоне ±0.05% классифицируется как FLAT
(практически безразличное движение, шум).

**Зачем такое разделение**: одно число «323.14 руб» труднее понять, чем
структурированный ответ «вверх на 0.35%, высокая уверенность, в диапазоне
321–326». Первое — техническая выдача, второе — actionable signal.

### Q: Что конкретно модель выдаёт на выходе?

**A**: Точечный прогноз **цены закрытия** на 3 будущих торговых дня, плюс
обвязка из доверительных интервалов, направления и сравнения с baseline.

**Один прогон (на один тикер) даёт:**

| Артефакт | Описание |
| --- | --- |
| **Прогноз Close** (×3) | Точечная цена закрытия для дней t+1, t+2, t+3 |
| **CI** (×3) | Нижняя и верхняя границы (5%/95% по умолчанию, или 25%/75% в `--ci-mode narrow`) |
| **Даты прогноза** (×3) | Учитывают торговый календарь — выходные и праздники пропускаются |
| **Direction** (×3) | Up / Down относительно последней известной цены |
| **График .jpg** | Историческая кривая + 3 точки прогноза + полоса CI |
| **Лог .txt** | Все числа в текстовом виде (`outputs/.../backtest/*.txt`) |

В **бэктест-режиме** дополнительно сравниваются прогноз с реальной ценой
на ту же дату, и считаются метрики качества: Error % (абсолютная и
относительная), Direction Accuracy, CI Coverage, R² on returns, IC,
Naïve comparison.

**Пример реального вывода** (SBER, бэктест 2026-05-05, run v16-B1.1):

```text
1-day forecast (2026-05-06):
  Real:         319.90 RUB
  Forecast:     320.02 RUB | Error: 0.12 RUB (0.04%)
  Naive:        321.20 RUB | Error: 1.30 RUB (0.41%)
  CI:           [311.44, 324.65]
  Direction:    down (real: down) [ok]

2-day forecast (2026-05-07):
  Real:         318.77 RUB
  Forecast:     315.28 RUB | Error: 3.49 RUB (1.10%)
  CI:           [300.23, 320.27]
  Direction:    down (real: down) [ok]

3-day forecast (2026-05-08):
  Real:         320.39 RUB
  Forecast:     314.35 RUB | Error: 6.04 RUB (1.88%)
  CI:           [304.92, 322.42]
  Direction:    down (real: down) [ok]

AVERAGE METRICS:
  Model Error:    1.01% (avg) | Naive Error: 0.47% — модель хуже Naive
  Direction Accuracy: 100% | CI Coverage: 100%
```

**Что важно понимать**:

- Это **regression-модель**, не классификация. Direction выводится из
  знака `pred − last_close`, а не учится напрямую.
- На выходе **не одно число**, а структурированный пакет: цена + CI +
  направление + diagnostic metrics. Это критично — точечный прогноз без
  CI и сравнения с Naïve мало что говорит.
- **3 горизонта одновременно** — для каждого обучается отдельная модель
  (MIMO, см. соответствующий вопрос), нет накопления ошибки.

### Q: В чём практическая ценность результата?

**A**: Точечный прогноз сам по себе ограничен — рынок шумный, и одно число
«315.28 RUB на 2026-05-07» вряд ли стоит много в торговле. **Истинная
ценность модели — в комплекте**:

1. **Направление** (`down`/`up`) — сильнее, чем точная цифра, потому что
   говорит «покупать или продавать» вместо «угадать на копейку».
2. **CI** показывает диапазон риска: если реальная цена обычно попадает
   в CI, можно строить ордера-стопы; если нет — модель плохо откалибрована.
3. **Сравнение с Naïve** говорит, есть ли вообще польза от модели на
   конкретном тикере. Без этого высокий R² на ценах — иллюзия (см.
   соответствующий вопрос).

То есть результат — **не «цена будет X»**, а скорее: **«цена скорее всего
пойдёт ВНИЗ, в коридоре от Y до Z, и мы это утверждаем увереннее, чем
тривиальный прогноз "цена не изменится"»**.

Это академически защитимая трактовка вывода модели. В реальной торговле
ни один из этих сигналов отдельно недостаточен — нужен ещё risk management,
учёт комиссий и т.д. (см. раздел про ограничения).

### Q: В чём вообще польза нашего продукта? Это для торговли?

**A**: **Это НЕ продукт для торговли.** Объясняю тремя слоями.

**Чем продукт НЕ является**:

- **Не торговая система**. На 3 точках бэктеста IC шумит ±0.5, на одном
  плохом дне модель проигрывает Naïve в 5 раз. Без risk management, учёта
  комиссий и тестирования на 100+ датах ставить деньги нельзя.
- **Не гарантия прибыли**. Эффективность рынков говорит: если бы такая
  простая модель давала edge, HFT-фонды бы её уже эксплуатировали.
- **Не предсказание правды**. Прогноз 323 руб ≠ «цена будет 323». Это
  «среди возможных исходов наиболее вероятная зона — 321–326».

**Чем продукт ЯВЛЯЕТСЯ**:

1. **Академическое исследование архитектуры стэкинга** — основная ценность.
   Дипломная работа = ответ на вопрос «можно ли в стэкинге LSTM + XGBoost
   получить рост качества по сравнению с одиночными моделями». Ответ:
   «частично — да, на стабильных тикерах; ограничения известны».

2. **Воспроизводимый методологический baseline**. Любой студент или
   исследователь после нас может взять этот код, запустить и получить
   **те же числа** (RANDOM_SEED=42). Это значит, можно строить свои
   улучшения поверх — менять одну компоненту и видеть эффект.

3. **Каркас с риск-метриками вместо «volшебного числа»** — CI Coverage,
   R² on returns, IC, сравнение с Naïve. Это превращает «прогноз цены» в
   **«прогноз цены + честная оценка собственного качества»**.

4. **Учебная платформа** — показывает, **как** на практике делается feature
   engineering, walk-forward, stacking, hyperparameter tuning, CI. От
   загрузки данных до интерпретации остатков.

**Что пользователь может реально делать с этим**:

| Сценарий | Как использовать |
| --- | --- |
| **Второе мнение к собственному анализу** | Запустить на тикере, посмотреть направление и CI — сравнить с тем, что думаешь сам |
| **Стресс-тест на разных режимах рынка** | Запустить на 5-10 датах, посмотреть, в каких условиях модель работает |
| **Базис для своего исследования** | Заменить LSTM на TFT/Mamba, посмотреть Δ; добавить sentiment — посмотреть Δ |
| **Отчёт для нетехнической аудитории** | «Модель утверждает, что вероятное направление SBER на завтра — вверх, с уверенностью 90%, цена в диапазоне 321–326» |

**Главный принцип**: ценность — не в **точке** прогноза, а в **процессе**,
который этот прогноз порождает и обосновывает.

## 1. Архитектура моделей

### Q: Почему LSTM + XGBoost + Ridge (стэкинг), а не одна модель?

**A**: Это ансамбль с дополняющими друг друга сильными сторонами.

- **LSTM** улавливает временные зависимости (моментум, последовательности).
- **XGBoost** работает с табличными признаками (технические индикаторы,
  фундаментальные показатели), устойчив к выбросам и переобучению.
- **Ridge meta-learner** учится взвешивать предсказания LSTM и XGBoost
  оптимально, причём веса (`coef_[0]`/`coef_[1]`) интерпретируемы.

Стэкинг в литературе по прогнозированию финансовых рядов — стандартный
подход, превосходящий одиночные модели на 5–15%.

### Q: Почему именно XGBoost, а не LightGBM или CatBoost?

**A**: XGBoost — наиболее устоявшийся и широко цитируемый gradient-boosting
фреймворк в академической литературе по финансовому прогнозированию.

Сравнение трёх популярных бустингов для нашей задачи:

| Параметр | **XGBoost** ✓ | LightGBM | CatBoost |
| --- | --- | --- | --- |
| Скорость на ~3000 строк | средняя | быстрее (~×1.5) | средняя |
| GPU support | ✓ | ✓ | ✓ |
| Quantile regression | нативный (`reg:quantileerror`) | через workaround | нативный |
| Категориальные фичи | требует one-hot | хорошо встроены | лучше всех |
| Стабильность на малых данных | устойчив | склонен к переобучению (leaf-wise growth) | устойчив |
| Цитирование в финансовых статьях | стандарт | растёт | реже |

**Конкретные причины выбора XGBoost у нас**:

- **Размер данных ~3000 строк**: ускорение LightGBM (×1.5) даёт +30 секунд
  на прогон — несущественно. На больших данных (millions) разница важнее.
- **Категориальных фичей мало** (day_of_week, month, quarter — все
  числовые), преимущество CatBoost не реализуется.
- **Quantile regression** для CI нативно поддержан в XGBoost через
  `reg:quantileerror` — это критично для нашей CI-схемы.
- **Стабильность на малых данных**: LightGBM с leaf-wise growth склонен
  к переобучению, что нежелательно в финансовых рядах с низким signal-to-noise.
- **Stable API** — XGBoost мало меняется между версиями, что важно для
  воспроизводимости дипломной работы.

**Когда стоило бы переключиться**:

- Большие данные (миллионы точек) → LightGBM
- Много категориальных фичей → CatBoost
- Если бы мы использовали другой sentiment-источник с категориальными
  embeddings — CatBoost мог бы быть лучше

Для нашего проекта XGBoost — рациональный default, и переход на альтернативы
не даст значимого выигрыша.

### Q: Почему LSTM получает только 7 признаков, а XGBoost — 43?

**A**: Чтобы LSTM не дублировал работу XGBoost, а специализировался на
«сыром временном» представлении.

LSTM получает только OHLCV + Price_Change_1 + Vol_Return_10 — минимум,
из которого можно учить временные паттерны. XGBoost видит все индикаторы
(MACD, RSI, BB, ATR…) и сам решает, какие важны через splits деревьев.

Если бы LSTM получал те же 43 признака — он бы дублировал feature engineering
XGBoost, и веса в Ridge перетасовались бы хаотично без видимого смысла.

### Q: Почему Ridge с `positive=True`?

**A**: Запрет отрицательных весов — защита от **артефактов
мультиколлинеарности**.

Без `positive=True` Ridge мог дать LSTM вес −0.136 (наблюдалось в v15.10).
Это **не** означает «LSTM предсказывает наоборот» — это OLS-артефакт:
когда LSTM и XGBoost сильно скоррелированы, регрессия может выдать любые
веса с большой дисперсией. Запрет отрицательных весов даёт более стабильный
и интерпретируемый ансамбль.

Цена решения: если LSTM реально предсказывает антитрендово, его вклад
будет полностью отброшен (вес = 0). Мы считаем это приемлемым tradeoff'ом.

### Q: Почему MIMO (прямое многошаговое), а не рекурсивное прогнозирование?

**A**: **MIMO** (Multi-Input Multi-Output, direct multi-step forecasting) —
для каждого горизонта обучается **отдельная модель**. Альтернатива
(рекурсивное прогнозирование): предсказать день 1, подать предсказание
на вход для дня 2, и т.д.

Почему MIMO выбран:

- **Нет накопления ошибки**. При рекурсивном подходе ошибка дня 1
  усиливает ошибку дня 2, та — ошибку дня 3. На горизонте 3 дня ошибка
  может вырасти в разы. MIMO лишён этой проблемы — каждая модель
  оптимизируется под свой конкретный горизонт.
- **Каждая модель оптимизирована под цель**. Для h=1 модель учится
  предсказывать «завтра», для h=3 — «через 3 дня». Это разные задачи
  с разным сигнал-к-шуму, и отдельные модели справляются лучше.
- **Стандарт в академической литературе** для multi-step time series
  (Bontempi & Taieb, 2012; обзоры по financial forecasting).

Цена: **3× обучения** (3 раздельных пайплайна: каждый со своими LSTM,
XGBoost, Ridge). Это значительная нагрузка, но компенсируется качеством.

Итого: 3 горизонта × (3 LSTM в ансамбле + XGBoost + meta + 2 CI-модели)
= **54 модели** на один тикер. Подробно — в `architecture.md`.

### Q: Что такое квантильная регрессия и как она строит CI?

**A**: **Квантильная регрессия** — XGBoost с loss-функцией
`reg:quantileerror`, которая обучается предсказывать конкретный
**перцентиль** распределения, а не среднее.

Обычная регрессия минимизирует `(y - pred)²` → предсказывает среднее.
Квантильная регрессия минимизирует асимметричный loss → предсказывает
заданный перцентиль (например, 5% или 95%).

**Как мы строим CI**:

1. После walk-forward собираем ~600 **OOS-остатков** (`actual - pred`).
2. Обучаем 2 квантильные XGBoost-модели на этих остатках:
   - `lower_model`: `quantile_alpha=0.05` (нижний 5-й перцентиль)
   - `upper_model`: `quantile_alpha=0.95` (верхний 95-й перцентиль)
3. Финальный CI:
   `[pred + lower_residual_quantile, pred + upper_residual_quantile]`

**Почему квантильная регрессия лучше параметрического CI** (например,
`pred ± 1.96·σ`):

- **Не требует допущения о нормальности остатков**. На финансовых рядах
  остатки часто имеют тяжёлые хвосты — нормальная аппроксимация занижает
  ширину CI в кризисах.
- **Адаптивный**: квантильные модели сами по фичам тестового окна
  определяют, какой ширины CI нужен (волатильные периоды → шире).
- **Покрытие соответствует теории**: 90% CI должен накрывать 90%
  будущих значений; квантильная регрессия даёт это эмпирически на OOS.

**Ограничение**: на 3 точках бэктеста CI Coverage всегда 0% или 100%.
Для значимой оценки покрытия нужны 10+ дат бэктеста (см. multi-date
бэктест в `improvements.md`).

### Q: Чем отличается `--ci-mode wide` от `--ci-mode narrow`?

**A**: Это два режима построения доверительных интервалов с разной
**философией риска**.

| Параметр | `wide` (default) | `narrow` |
| --- | --- | --- |
| Перцентили | 5 / 95 | 25 / 75 |
| Историческое окно для residuals | вся история обучения | последние 3 года |
| Ширина CI | широкая | узкая |
| Целевое покрытие | 90% | 50% |
| Учёт кризисов | да (учитываются 2008, 2014, 2020, 2022) | нет (только недавний режим) |

**Когда использовать `wide`** (по умолчанию):

- Академическая работа, дипломная защита
- Когда важна честная оценка риска
- Долгосрочный прогноз (1-3 дня — формально краткосрочный, но рынок РФ
  волатилен в кризисы)
- Тикеры с большой исторической волатильностью

**Когда использовать `narrow`**:

- Прикладная задача — текущий режим рынка спокойный
- Не нужна устойчивость к кризисам
- Цель — узкий CI для принятия торговых решений

**Тонкий момент**: `narrow` за последние 3 года игнорирует кризисные
данные. Это удобнее в спокойном рынке, но опасно — если завтра кризис,
CI будет занижен.

В нашей дипломной работе **по умолчанию используем `wide`** как более
академически защитимый выбор.

### Q: Почему walk-forward с 3 сплитами (80/85/90%)?

**A**: Расширяющееся окно (expanding window) — стандарт для временных рядов.
3 сплита — компромисс между надёжностью валидации и скоростью обучения.

- 1 сплит → high variance в результатах, нет защиты от переобучения
- 5+ сплитов → каждый сплит обучается на маленьком окне, что даёт
  плохие модели на ранних сплитах
- 3 сплита (80/85/90%) → каждый имеет минимум 80% истории для обучения
  и достаточно тестовых точек для статистики

### Q: Что такое OOS (Out-of-Sample), откуда берётся и зачем используется?

**A**: **OOS** (Out-of-Sample) — это данные, которые модель **не видела во
время обучения**, используемые для честной оценки её способности обобщать
на новые наблюдения.

Противоположность OOS — **in-sample** данные, на которых модель училась.
Если модель показывает блестящие метрики на in-sample, но плохие на OOS —
это переобучение (overfitting).

**Откуда OOS берётся в нашем проекте**:

В walk-forward валидации каждый из 3 сплитов даёт свою пару train/test:

```text
Сплит 1: train на первых 80% истории → test на следующих 5% (это OOS №1)
Сплит 2: train на первых 85% истории → test на следующих 5% (это OOS №2)
Сплит 3: train на первых 90% истории → test на следующих 10% (это OOS №3)
```

Модель не видит test-окно при обучении на каждом сплите → предсказания на
этих окнах являются OOS-предсказаниями. Реальные значения в этих окнах —
OOS-таргеты. Разница (`actual - predicted`) — **OOS-остатки** (residuals).

**Где OOS используется конкретно**:

1. **OOS-метрики** (RMSE, MAE, R²): считаются в каждом сплите между
   OOS-таргетами и OOS-предсказаниями, потом усредняются. Это `avg R²`,
   который мы видим в логе. Эти метрики показывают, как модель работает
   на «новых» данных.

2. **OOS-остатки → доверительные интервалы (CI)**: после walk-forward
   собираются все OOS-остатки (~600 точек) и на них обучаются 2 квантильные
   XGBoost-модели (5/95 или 25/75 в зависимости от `--ci-mode`). Это даёт
   CI вокруг финального прогноза: `pred ± residual_quantile`. Поскольку
   обучение CI идёт на **out-of-sample остатках**, ширина CI честно
   отражает реальную ошибку модели, а не оптимистичную in-sample ошибку.

3. **OOS-диагностика** (Ljung-Box): тест автокорреляции в OOS-остатках
   показывает, есть ли несхваченная моделью структура в ошибках. Если
   остатки **не белый шум** (Ljung-Box p < 0.05), это сигнал, что модель
   что-то упускает.

**Почему именно OOS важен**:

In-sample метрики всегда оптимистичны: модель видела эти данные, она к ним
подстроилась. Реальное качество модели проявляется только на данных, которые
она не видела. Для финансовых рядов это особенно критично: рынок постоянно
меняется, и in-sample R² = 0.99 ничего не говорит о завтрашнем дне.

**Связь с бэктестом**: бэктест на конкретной дате (например, 2026-02-01) —
это **дополнительный OOS-тест**: модель обучается на данных до этой даты,
а потом предсказывает следующие 1-3 дня, которых не видела вообще. Walk-forward
OOS — это OOS внутри обучающей истории, бэктест OOS — за её пределами.

## 2. Целевая переменная и нормализация

### Q: Почему предсказываем цену, а не направление (UP/DOWN)?

**A**: Регрессия даёт больше информации: и направление, и величину движения,
и доверительный интервал.

Классификация (UP/DOWN/FLAT) была бы проще, но потеряли бы возможность
оценить риск (CI), магнитуду движения, и стандартные регрессионные метрики
(RMSE, MAE). Мы получаем direction accuracy "бесплатно" из регрессионного
прогноза через знак изменения относительно последней цены.

### Q: Почему MinMaxScaler, а не StandardScaler?

**A**: MinMax даёт диапазон [0,1] — естественный для LSTM с нелинейностями,
не приводит к экстремальным значениям.

StandardScaler центрирует на нуле и масштабирует на std, но при наличии
выбросов в истории (резкие скачки во время кризисов) распределение становится
тяжёлохвостным, что хуже для градиентного спуска LSTM.

Для log-returns мы пробовали StandardScaler — не дало улучшения (см. v16.0
в CHANGELOG).

### Q: Почему НЕ предсказываем log-returns? (отрицательный опыт v16.0 и v16-D)

**A**: Пробовали дважды — оба раза провал из-за низкого signal-to-noise.

**v16.0** (log-return target + MSE scoring):

- LSTM получал нулевой вес в Ridge на всех 5 проверенных датах
- Direction Accuracy 0% на 2026-05-05
- Optuna выбирал Ridge alpha 89-99 (упор в верхнюю границу) →
  модель = intercept ≈ среднее log-return ≈ константа

**v16-D** (log-return target + R² scoring, после успеха B1.1 на price target):

- На PLZL (extreme growth, 60×) — успех (Direction 100%, Error 1.59%)
- На SBER/LKOH/GAZP — катастрофа (Direction 0%)
- "Победа" на PLZL оказалась случайным совпадением: модель предсказывала
  среднюю log-доходность (положительную для растущей акции), что совпало
  с реальным трендом

**Корень проблемы**: дисперсия log-returns маленькая (~±2%). Любая
nontrivial модель имеет очень негативный R² в кросс-валидации из-за шума.
Optuna выбирает «predict mean log-return» как наименьшее зло.

**Вывод**: log-returns не работают с MSE/R² scoring при walk-forward
кросс-валидации. Решение требует либо custom directional loss, либо
rolling-window нормализации цен (ещё не реализовано — см. раздел 6).

### Q: Почему у нас ДВА MinMaxScaler: `scaler` и `close_scaler`?

**A**: Они решают разные задачи и применяются к разным частям пайплайна.

| Скейлер | На чём обучен | Что нормализует | Где используется |
| --- | --- | --- | --- |
| `scaler` | все 43 фичи (`data[features]`) | **вход** моделей (LSTM + XGBoost) | при формировании `X` и `X_lstm` |
| `close_scaler` | только колонка `Close` | **таргет** (`y`) и **инверсия прогнозов** | при формировании `y` и при выводе `pred_close` в рублях |

**Зачем два, а не один**:

1. **Чистая инверсия прогнозов**. Модель выдаёт `pred` в [0, 1] (scaled).
   Чтобы получить реальные рубли, нужен `inverse_transform`. Если бы мы
   использовали общий `scaler` (который знает о 43 фичах), нам пришлось бы
   подавать в `inverse_transform` фейковую матрицу с pred_close в нужной
   колонке и нулями в остальных — это error-prone и неуклюже.

2. **Изоляция изменений**. Если завтра решим иначе нормализовать таргет
   (например, использовать `log(close)`), нужно поменять только
   `close_scaler`, не трогая `scaler`.

3. **Стандартная практика в ML-пайплайнах**: отдельный input transformer
   и target transformer — sklearn-style design (см. `TransformedTargetRegressor`).

**Альтернатива «один scaler»**: можно было бы получить min/max для Close
из общего `scaler` через `scaler.data_min_[close_idx]` и
`scaler.data_max_[close_idx]`. Работает, но более fragile (что если
порядок фич изменится?). Два scaler — explicit вместо implicit.

### Q: Зачем добавили relative features (Close_to_SMA10, BB_Position, …)?

**A**: Дать модели контекст «насколько цена отклонилась от своей нормы»
вместо абсолютных уровней индикаторов.

Без relative features модель видит `SMA_20 = 320 руб` и `Close = 322 руб`
как два почти одинаковых числа. С relative features `Close_to_SMA20 = 1.006`
явно говорит «цена на 0.6% выше скользящей средней» — это сигнал
mean-reversion, который модель ловит напрямую.

**Побочный эффект**: relative features сделали XGBoost настолько сильным,
что вытеснили LSTM из ансамбля (вес 0.000 на большинстве дат). Это
обнаружено в v16-B2 — см. CHANGELOG.

## 3. Метрики оценки качества

### Q: Почему R² на ценах ≈ 0.80 — не показатель качества модели?

**A**: Цены акций — почти прямая линия с небольшими колебаниями.
Тривиальный прогноз "цена не изменится" уже даёт R² > 0.8 без всякой модели.

Это иллюзия высокой точности из-за **трендовости ряда**. Корректная мера —
R² на дневных доходностях (returns), который у честных моделей в диапазоне
0.01–0.05.

### Q: Что такое R² на доходностях и почему он часто отрицательный?

**A**: R² на доходностях — это R² для предсказания **процентного изменения**
цены, а не самой цены.

Формула: R² = 1 - SS_res/SS_tot, где `y = (close[t+h] - close[t])/close[t]`.

Часто отрицательный, потому что:

- Дисперсия доходностей маленькая (~±2%)
- Любая ошибка в прогнозе становится большой относительно дисперсии
- Бэктест на 3 точках статистически шумный

**Это не баг — это честная метрика.** Положительный R² на доходностях
встречается редко даже у профессиональных моделей.

### Q: Что такое IC (Information Coefficient)?

**A**: Spearman ранговая корреляция между предсказанными и реальными
доходностями.

В отличие от R², который чувствителен к магнитуде, IC измеряет только
**правильность ранжирования**: угадала ли модель, что период X будет лучше
периода Y, независимо от точных чисел.

В quant-индустрии:

- IC > 0.05 — значимо
- IC > 0.10 — сильный сигнал
- IC < 0 — модель ранжирует **наоборот**

### Q: Зачем сравнение с Naïve baseline в каждом бэктесте?

**A**: Чтобы доказать, что модель **добавляет ценность** поверх тривиального
прогноза.

Naïve baseline: «цена завтра = цена сегодня». На горизонтах 1-3 дня этот
прогноз даёт ошибку ~0.3–1.5% — уже неплохо. Если наша модель не бьёт
Naïve — она бесполезна, какой бы красивый R² на ценах ни показывала.

**Это самый сильный контраргумент против наивных «AI-моделей»** в
дипломных работах с R² 0.95+ без сравнения с baseline.

### Q: Почему Direction Accuracy важнее, чем абсолютная ошибка в %?

**A**: Для практического применения (принятие решения о покупке/продаже)
важно **угадать направление**, а не точное число.

Прогноз «цена 320 при реальной 318» (ошибка 0.6%, направление неправильное)
бесполезен для трейдера — он ожидал рост, а получил падение. Прогноз
«цена 325 при реальной 322» (ошибка 0.9%, направление правильное)
даёт верный сигнал к покупке.

В академической работе Direction Accuracy — менее интерпретируемая, чем
RMSE, но более релевантная для принятия решений.

## 4. Гиперпараметры и валидация

### Q: Почему R² scoring для Ridge alpha вместо MSE? (v16-B1.1)

**A**: MSE scoring приводил к нулевому весу LSTM в Ridge на тикерах с
relative features.

После добавления relative features XGBoost стал настолько хорош, что
Ridge с MSE scoring давал ему весь вес (LSTM = 0.000 на 5/5 дат). R² scoring
учитывает не только MSE, но и **относительное улучшение над baseline
prediction = mean(y)**, поэтому даёт LSTM ненулевой вес там, где он
улучшает прогноз.

Результат: LSTM получил вес 0.005-0.204 на 3/5 дат. На 2025-09-15 модель
улучшилась на 27% (Error 1.89% → 1.38%) благодаря оживлению LSTM.

### Q: Если R² теперь scoring — почему мы продолжаем видеть R² в выводе модели?

**A**: Это **три разные R²**, легко перепутать. Они служат разным целям и
независимы друг от друга.

| Где | Что считается | Назначение |
| --- | --- | --- |
| **R² scoring** (внутри `optimize_ridge_alpha`) | R² между предсказаниями Ridge и реальными значениями на cross-val фолдах | **Выбор** оптимального alpha из 30 trials Optuna |
| **avg R²** (в логе walk-forward) | R² между предсказанными и реальными ценами на OOS-окнах | Информационная метрика качества модели на исторических OOS |
| **R² on returns** (в бэктесте) | R² между предсказанными и реальными доходностями (%) на 3 точках | Честная академическая метрика для конкретной даты |

**Что изменило B1.1**:

- **МЕНЯЕТ:** как Optuna выбирает Ridge alpha (внутренняя оптимизация)
- **НЕ МЕНЯЕТ:** что мы выводим в логах (метрики качества)

Раньше Optuna минимизировал MSE при выборе alpha → XGB получал всю работу
(LSTM weight = 0). Теперь Optuna максимизирует R² → выбирает alpha, который
даёт LSTM небольшой ненулевой вес.

**Видимые эффекты**:

- Ridge alpha теперь чуть другой (~0.05 вместо ~0.0011)
- LSTM weight ненулевой на 3 из 5 дат (было 0/5)
- Avg Error% улучшился маргинально (1.30% → 1.27%)
- **avg R² в логе продолжает считаться той же формулой** — это наша
  информационная метрика, она не зависит от выбора scorer'а

**Аналогия**: ты выбираешь машину. R² scoring = твой критерий выбора
(«расход топлива»). После покупки в анкете машины всё равно пишутся
**другие поля**: цвет, мощность, объём. Ты сменил критерий выбора с «цена»
на «расход» — машины разные, но поля анкеты те же.

Это разделение **scoring vs reporting** — стандартная практика в ML.

### Q: Почему НЕ correlation scorer? (отвергнутый эксперимент v16-B1)

**A**: Correlation scorer поощрял Ridge alpha → ∞ (предсказание константы).

Pearson correlation вознаграждает «направленные шумные предсказания» вне
зависимости от их абсолютной точности. Optuna честно нашла alpha=96 (близко
к upper bound), при котором коэффициенты Ridge крошечные, и предсказание
≈ mean training set.

Результат: LSTM получил вес 0.371 (хорошо!), но Model Error вырос до 8.57%
(катастрофа), потому что предсказывалась средняя цена ~256 руб при реальной
~310 руб.

R² scoring оказался компромиссом: даёт LSTM вес без коллапса точности.

### Q: Почему Optuna иногда даёт результаты ХУЖЕ default параметров?

**A**: Optuna минимизирует ошибку на walk-forward кросс-валидации
(исторические данные), но это не гарантирует, что найденные параметры будут
лучшими для **новой даты**, которую модель не видела.

Это классическая проблема **gap between validation and out-of-sample test**.
Особенно ярко проявилось на LKOH (Direction Accuracy 100% → 0% после
Optuna) и GAZP (67% → 33%).

Default-параметры из `config.py` (изначально настраивались на SBER) оказались
**более робастными** на других тикерах, чем Optuna-оптимизация под каждый
тикер отдельно.

**Это академически интересный вывод**: универсальные параметры могут
работать лучше per-ticker оптимизации из-за переобучения на холдаут.

### Q: Раньше Optuna улучшал результаты — что изменилось в v16?

**A**: На самом деле «раньше» — иллюзия: в v15 мы напрямую не сравнивали
«Optuna vs default» на одной дате/тикере. В benchmarks.md все кросс-тикерные
прогоны (v15.5 на 2024-10-14 и 2024-03-15) делались **с дефолтными
параметрами**, а отдельные Optuna-прогоны не сопоставлялись с дефолтами.

Поэтому корректная формулировка: «в v16 мы впервые провели прямое
сопоставление Optuna vs default, и обнаружили патологию».

**Почему патология появилась именно в v16**:

1. **Добавление 4 relative features увеличило размерность пространства фич**.
   Чем больше фич, тем больше у Optuna возможностей подобрать
   гиперпараметры, которые «случайно» хорошо работают на конкретных
   walk-forward windows, но плохо обобщаются.

2. **Walk-forward validation на 3 сплитах статистически шумна**. На каждом
   сплите ~150-300 тестовых точек. С 30 trials Optuna найдёт «лучшие»
   гиперпараметры по этой шумной метрике, что часто = переобучение на шум.

3. **R² scoring (B1.1) более чувствителен к выбросам**, чем MSE — добавляет
   ещё немного шума в Optuna-объект.

**Способы исправить (не реализованы)**:

| Подход | Сложность | Эффект |
| --- | --- | --- |
| Меньше trials (10-15 вместо 30) | низкая | меньше overfitting на validation |
| Ансамбль top-N trials вместо best-1 | средняя | усреднение лучших, защита от outlier |
| Nested cross-validation | высокая | принципиально правильное решение |
| Больше walk-forward сплитов (5-7) | средняя | менее шумная validation метрика |
| Early stopping Optuna при плато | низкая | избегает «доводки» до переобучения |
| Bayesian model averaging | высокая | веса всех trials, не только лучшего |

**Прагматичный вывод для нашего проекта**:

- Использовать `--optimize` ОДИН раз для подбора стартовых параметров на
  одном эталонном тикере (SBER)
- Зафиксировать эти параметры в `config.py` как глобальные дефолты
- НЕ переопимизировать под каждый тикер отдельно — выигрыш мнимый
- Это и так было нашим практическим режимом работы; теперь — обоснованно

### Q: Почему `LOOK_BACK=30` дней — а не 60, 90 или 5?

**A**: 30 дней — приблизительно **один торговый месяц**. Это компромисс между
объёмом исторического контекста и обучаемостью LSTM.

**Почему именно ~30**:

- **Захватывает месячную сезонность**: ежемесячные отчёты, дивидендные
  периоды (~30-45 дней до объявления), смена настроений рынка
- **Достаточно для momentum-паттернов**: SMA(10), EMA(20), MACD —
  все индикаторы укладываются в окно
- **LSTM эффективно обучается на коротких-средних последовательностях**:
  длина 30 — sweet spot, где LSTM ловит зависимости без vanishing gradient

**Почему НЕ дольше (60-90 дней)**:

- LSTM на длинных последовательностях обучается медленнее (квадратичная
  сложность от длины)
- Дальние дни в прошлом несут меньше сигнала для прогноза на 1-3 дня —
  закон убывающей предельной полезности
- В наших данных (3000-3700 точек) увеличение LOOK_BACK до 90 уменьшает
  количество обучающих окон на ~6% — менее эффективное использование данных

**Почему НЕ короче (5-10 дней)**:

- Слишком короткие последовательности не дают LSTM преимущества — для
  такого окна XGBoost на сплющенных фичах справляется не хуже
- Не успевает захватить недельные и месячные эффекты
- Sliding window становится «локальной средней», теряя долгосрочный контекст

**Эмпирически**: 30 — стандарт в академической литературе по прогнозированию
финансовых временных рядов (Borovykh et al., 2017; Sezer & Ozbayoglu, 2020).
Мы не пробовали оптимизировать через Optuna — это потенциальное направление
для будущих экспериментов, но прирост ожидается небольшой.

### Q: Что такое `ENSEMBLE_SEEDS = [42, 7, 123]` и почему 3 разных seed?

**A**: Это **ансамбль из 3 LSTM**, каждый обучается с своим random seed
для инициализации весов. Финальный прогноз — среднее их предсказаний.

**Зачем нужно**:

LSTM-обучение **стохастично**: Adam optimizer + mini-batch sampling +
случайная инициализация весов дают разный результат при одинаковых данных
и гиперпараметрах. На один и тот же тикер один обученный LSTM может дать
прогноз 320 руб, другой — 318. Без ансамбля выбор «правильного» LSTM был бы
случайным.

**Как работает**:

```python
ENSEMBLE_SEEDS = [42, 7, 123]
# В цикле walk-forward:
lstm_preds_avg = np.mean(
    [train_lstm(seed=s).predict(X) for s in ENSEMBLE_SEEDS], axis=0
)
# Затем lstm_preds_avg идёт в Ridge meta-learner.
```

**Эффект**:

- **Снижение дисперсии**: усреднение N независимых моделей уменьшает шум
  в `1/sqrt(N)` раз. С N=3 → ~×0.58 (на 42% меньше)
- **Стабильность бенчмарков**: при перезапуске одной и той же конфигурации
  ансамбль даёт похожие результаты (без ансамбля разброс был до ±0.5%
  Error на SBER)

**Почему именно 3**:

- 1 → нет ансамбля, высокая дисперсия
- 3 → значимое снижение шума при умеренной цене обучения (3× LSTM)
- 5-10 → ещё лучше, но прирост ×0.45 → ×0.32 при тройной цене

Выбор 3 — баланс эффект/время. Конкретные значения seeds (42/7/123)
произвольные — важно только что они разные.

**Цена**: время обучения LSTM ×3. Это значительно (LSTM — узкое горлышко
пайплайна), но компенсируется стабильностью результатов.

### Q: Почему фиксированный RANDOM_SEED=42?

**A**: Воспроизводимость результатов между прогонами — критично для
бенчмарков и научной работы.

Seed 42 устанавливается для всех источников случайности: `random`, `numpy`,
`torch`, `torch.cuda`. Без этого LSTM при каждом запуске будет давать
разные веса (Adam стохастический), и сравнение версий (v15 vs v16)
станет невозможным.

Также используется `ENSEMBLE_SEEDS = [42, 7, 123]` для N=3 LSTM в
ансамбле — каждый со своим сидом для diversity.

## 5. Признаки (Feature Engineering)

### Q: Какие именно relative features добавлены и зачем каждый?

**A**: 4 признака, каждый кодирует свой аспект mean-reversion:

- `Close_to_SMA10` = `close / SMA(10)` — отклонение от короткого тренда
- `Close_to_EMA20` = `close / EMA(20)` — отклонение от среднесрочного тренда
- `BB_Position` = `(close - BB_Lower) / (BB_Upper - BB_Lower)` —
  позиция в Боллинджеровом канале (0=низ, 1=верх)
- `Close_ZScore_20` = `(close - mean(20)) / std(20)` — z-score за 20 дней,
  стандартный индикатор «насколько цена нетипична»

Все четыре scale-invariant: дают одинаковый сигнал и для SBER (~320 руб),
и для PLZL (~2700 руб).

### Q: Зачем Granger pre-screening признаков?

**A**: Формальное обоснование, что включаемые признаки **причинно влияют** на
будущие цены, а не просто скоррелированы.

Granger causality test проверяет: помогает ли история признака X лучше
предсказать будущее Close, чем только сама история Close. Признаки с
p ≥ 0.05 (нет статистической связи) исключаются динамически — это особенно
важно для макропризнаков (USD/RUB, ставка ЦБ, Brent), которые могут быть
полезны для одних тикеров и бесполезны для других.

### Q: Как мы используем данные о дивидендах и откуда их берём?

**A**: Дивиденды реализованы как **3 time-varying признака** (`fundamentals_loader.py`),
а не как snapshot значение. Это критично: одного числа «дивдоходность 10%» недостаточно — важно, **где сейчас находится тикер в дивидендном цикле**.

**Три признака**:

| Признак | Что значит | Когда меняется |
| --- | --- | --- |
| `div_days_to_next` | Дней до следующей даты закрытия реестра | Уменьшается каждый день, как только дивиденд объявлен |
| `div_next_amount` | Размер объявленного дивиденда (руб./акцию) | Меняется в момент объявления |
| `div_days_since_last` | Дней с последней даты закрытия реестра | Монотонно растёт, сбрасывается после выплаты |

**Почему именно так**:

Цена акции делает прогнозируемые движения в окрестности дивидендов:

- За 2-4 недели до закрытия реестра: рост от спроса
- После закрытия реестра: «дивидендный гэп» вниз на сумму дивиденда
- Между выплатами: накопление ожиданий

Эти эффекты систематические и значимые. Без дивидендных признаков модель видит «странные» падения цен в дни закрытия реестра и не может их объяснить.

**Источник**: MOEX ISS API напрямую,
`https://iss.moex.com/iss/securities/{ticker}/dividends.json`. Парсятся
поля `registryclosedate` и `value` (сумма дивиденда). Работает для любого
тикера MOEX (SBER, GAZP, LKOH, GMKN, …) — никакого ручного списка тикеров не требуется.

**Защита от look-ahead bias** (критично!):

Российские эмитенты объявляют дивиденды за 2-4 недели до закрытия реестра. Если бы мы использовали `div_days_to_next` и `div_next_amount` для всех будущих дат — модель «видела бы будущее» в исторических данных.

Решение: окно `_ANNOUNCE_WINDOW = 45` дней. Признаки ненулевые только если до даты закрытия реестра ≤ 45 дней — т.е. на этот момент дивиденд **уже точно объявлен** на бирже. До 45 дней — сентинель 999 (= «нет информации»).

**Что если API недоступен**: возвращается DataFrame с сентинелями (999) + warning в лог. Модель продолжает работать, просто без дивидендной информации.

**Где видно в логе**:

```text
dividends SBER: 6 выплат загружено, 276 дней в announce-окне (45 дн.), диапазон 2014-01-06 — 2026-05-12
```

«276 дней в announce-окне» = в стольких днях за всю историю SBER признак был ненулевым (~7% от общего числа дней).

### Q: Какие у нас системы кэширования данных?

**A**: Один полноценный дисковый кэш (для макро) + два уровня in-memory sharing внутри прогона. Дивиденды и фундаменталии кэша **не имеют** — загружаются каждый прогон, но переиспользуются для всех горизонтов.

**Уровень 1: дисковый кэш макроданных** (`.macro_cache.csv`)

Местоположение: корень проекта, файл в `.gitignore` (рабочий артефакт, не для VCS).

| Параметр | Значение |
| --- | --- |
| Файл | `.macro_cache.csv` |
| Структура | `Date, usd_rub_hist, cbr_rate, brent_price, imoex, rtsi` |
| Размер сейчас | ~4500 строк (2014-01-01 → текущая дата) |
| Refresh window | последние **7 дней** перезагружаются всегда (`_CACHE_REFRESH_DAYS=7`) |

**Логика кэша**:

- При старте: если файл есть, читаем покрытый диапазон
- Если диапазон покрывает запрос → используем кэш, но последние 7 дней перезагружаем (макроданные могут уточняться задним числом — например, ЦБ публикует ставку с задержкой)
- Если кэш не покрывает (новые даты) → дозагружаем недостающее, мержим, сохраняем
- При недоступности источника → возвращаем кэш с warning

**Скорость**: при холодном старте 5 макропризнаков загружаются ~30-60 секунд (5 параллельных HTTP-запросов через ThreadPoolExecutor). С кэшем — мгновенно (~50 мс на чтение CSV).

**Уровень 2: in-memory sharing внутри прогона** (~10× ускорение)

Без sharing каждый из 3 горизонтов независимо вызывал бы `load_macro_data()` + `load_dividend_features()` + `get_fundamentals()` = 3-кратное дублирование HTTP-запросов.

Решение: загружаем **один раз** в `run_backtest()` или main-функции, передаём как параметры в `prepare_and_train_model()` через аргументы `macro_data=`, `fund_data=`, `div_data=`:

```python
# Loading macro data once for all horizons...
shared_macro = load_macro_data(start, end)
shared_div   = load_dividend_features(ticker, start, end)
shared_funds = tinkoff_loader.get_fundamentals(ticker)

for h in [1, 2, 3]:
    prepare_and_train_model(..., macro_data=shared_macro, fund_data=shared_funds, div_data=shared_div)
```

**Уровень 3: GPU-память (cache)** — `torch.cuda.empty_cache()` вызывается после walk-forward, чтобы освободить VRAM от промежуточных LSTM-моделей. Не «кэш на чёрный день», а аккуратная утилизация GPU.

**Чего НЕТ (намеренно)**:

- **Кэш дивидендов на диск** — данные меняются редко (раз в год на тикер), но мы их обновляем каждый прогон ради простоты. ~1 секунда на тикер — не критично.
- **Кэш фундаменталий Tinkoff (P/E, ROE)** — Tinkoff API быстрый (1 запрос), кэш не оправдан.
- **Кэш биржевых свечей (OHLCV)** — данные обновляются каждый день, любой кэш быстро устарел бы. MOEX отдаёт всю историю SBER за ~5 секунд через `moexalgo`.

**Когда стоило бы добавить ещё кэшей**:

- Multi-date backtest (см. improvements.md): при прогоне 12 дат подряд можно было бы кэшировать предобработанные фичи. Сейчас каждый бэктест пересчитывает 43 признака с нуля.
- При переходе на минутные данные: тогда OHLCV-кэш станет необходимым (объём ×400).

### Q: Зачем макропризнаки (USD/RUB, ставка ЦБ, Brent)?

**A**: Российский рынок сильно зависит от макроусловий, особенно для
сырьевых тикеров (LKOH, GAZP).

- `usd_rub_hist` — ослабление рубля → рост экспортёров
- `cbr_rate` — рост ставки → давление на акции (альтернативная доходность
  в облигациях)
- `brent_price` — прямое влияние на нефтегаз
- `imoex` / `rtsi` — общий рыночный фон

Granger pre-screening сам решает, нужен ли макро для конкретного тикера.

## 6. Известные ограничения

### Q: Почему модель не работает на PLZL?

**A**: PLZL вырос в 60 раз за 12 лет (45 руб → 2744 руб). MinMaxScaler на
полной истории сжимает текущие цены к 0.96, а модель предсказывает в
середине диапазона → выдаёт ~1800 руб при реальных 2630 руб.

Это **фундаментальное ограничение MinMaxScaler на ряду с экстремальным
трендом**. Не специфика нашей модели — то же будет с любой регрессией на
абсолютных ценах.

**Возможные решения** (не реализованы):

- Rolling-window z-score (нормализация по скользящему окну ~120 дней)
- Log-prices вместо raw prices
- Ограничить training window последними 3-5 годами

### Q: Почему модель плохо работает на YDEX?

**A**: Структурный разрыв в истории: YNDX делистнули в июле 2024,
YDEX начал торговаться с июля 2024 как новая компания.

Мы добавили `is_post_restructure` дамми (v15.12), которая помогла
поднять avg R² с 0.405 до 0.454 (+4.9pp), но проблема не решена полностью.
Pre-restructure данные YNDX и post-restructure данные YDEX смешиваются в
одном тренировочном наборе.

**Ограничение известно и задокументировано** в improvements.md.

### Q: Почему модель плохо работает на T (бывший TCSG)?

**A**: TCSG делистнули в ноябре 2024 (Tinkoff → T-Bank). MOEX endpoint T
содержит склеенную историю TCSG + T, что технически работает, но смена
бренда / корпоративной структуры внесла break в данные.

Модель показывает Direction Accuracy 0% на 2026-02-01 — не может
адаптироваться к новой режиму торгов. Решение требует либо более длинной
истории с T (~год), либо явного учёта смены тикера.

### Q: Можно ли использовать модель в реальной торговле?

**A**: **Нет**, и вот почему:

1. **Бэктесты на 3 горизонтах (1, 2, 3 дня)** — статистически шумно,
   нужно тестировать на 100+ датах для значимых выводов
2. **Не учтены транзакционные издержки** (комиссия 0.05-0.1%, спред,
   slippage) — могут съесть весь edge
3. **Не учтена ликвидность**: для крупных позиций цена сдвигается при
   исполнении
4. **Direction Accuracy 67% на средней не означает 67% прибыли** — без
   risk management серия из 5 неверных угадок подряд может убить депозит
5. **Эффективность рынка**: модель использует только публично доступные
   данные. Если бы такая простая модель действительно работала, её бы уже
   эксплуатировали HFT-фонды.

Модель — академическое исследование архитектуры ансамбля, не торговая
система.

## 7. Визуализация

### Q: Что делает `presentation_output.py` и зачем отдельный модуль?

**A**: Это специализированный модуль для построения графиков **под слайды
дипломной защиты**, отделённый от стандартной визуализации.

**Что в нём специфично**:

- **Соотношение 16:9** — стандарт для проекторов и презентаций
  (вместо стандартного matplotlib 8:6, который хорошо смотрится на A4)
- **Русские подписи осей и легенды** — для защиты в русскоязычном вузе
- **90% CI как заливка** (полупрозрачный fill_between), а не две линии —
  читабельнее с расстояния 5 метров
- **PNG 1920×1080 @ 150 DPI** — оптимально для проектора (без потерь на
  Full HD, не raster при увеличении)
- **Упрощённая легенда**: только 2-3 ключевых элемента вместо технических
  деталей (RMSE/MAE по горизонтам не показывается)

**Зачем отдельный модуль, а не флаг внутри `stock_modelv16.py`**:

1. **Разделение ответственности**. Модель занимается прогнозированием,
   `presentation_output` — отрисовкой. Когда нужно поменять стиль слайда
   (другой шрифт, цвет под брендинг кафедры), правится только этот модуль.
2. **Без замусоривания основного скрипта**. Презентационная логика —
   ~150 строк matplotlib-конфигов. Внутри `stock_modelv16.py` это было бы
   шумом.
3. **Reuse**: можно вызвать из любого скрипта, который имеет `data`,
   `forecasts` и `confidence_intervals` — например, из ноутбука для
   проверки результатов перед защитой.

**Как вызывается**:

```bash
python stock_modelv16.py --ticker SBER --presentation --history-window 90
```

Флаг `--presentation` запускает `plot_presentation()` после стандартного
прогноза. `--history-window 90` ограничивает показываемую историю до
последних 90 торговых дней (иначе на 12 лет данных одна точка-прогноз
теряется).

### Q: Как правильно читать график CI? Это две линии или полоса?

**A**: На стандартном matplotlib-выводе (без `--presentation`) CI рисуется
**двумя линиями** — нижняя и верхняя границы. На презентационном
графике — **полупрозрачной полосой** (заливкой).

Обе формы кодируют одно и то же:

| Элемент | Стандартный график | Презентационный |
| --- | --- | --- |
| Прогноз модели | сплошная линия (синяя) | сплошная линия |
| Нижняя граница CI (5% percentile) | пунктирная линия снизу | нижний край заливки |
| Верхняя граница CI (95% percentile) | пунктирная линия сверху | верхний край заливки |
| Историческая цена | серая линия | серая линия |

**Как интерпретировать**:

- **Ширина полосы = неопределённость прогноза**. Чем шире — тем меньше
  модель уверена. Обычно CI расширяется с горизонтом (для h=3 шире, чем
  для h=1).
- **Положение реальной цены относительно полосы** (на бэктесте): если
  попала внутрь — CI Coverage засчитывает 1. Если ниже нижней границы —
  модель недооценила падение. Если выше верхней — недооценила рост.
- **Полоса 90% не значит «диапазон возможных цен»** — это 90% **массы
  вероятности**. Цена может выйти за CI в 10% случаев (по построению).

**Типичные ошибки чтения**:

1. **Считать, что узкий CI = хороший прогноз**. Узкий CI значит, что
   модель **уверена** в своём прогнозе. Если она при этом систематически
   мажет — узкий CI плохо (заниженная оценка риска).
2. **Считать CI Coverage = качество модели**. Coverage показывает только
   калибровку CI. Можно иметь Coverage 100% с гигантским CI и Coverage 0%
   с узким CI; обе ситуации плохие, но по разным причинам.

**Что смотреть на графике для защиты**:

- Историческая часть → видно поведение модели на типичных днях
- Прогнозная часть → ширина CI (показывает уверенность)
- Реальная цена (на бэктесте) → должна быть внутри CI для валидации

## 8. Технологии

### Q: Почему PyTorch вместо TensorFlow/Keras?

**A**: TensorFlow 2.10+ не поддерживает CUDA на Windows нативно.
LSTM на CPU занимал ~80% времени прогона.

Миграция на PyTorch (cu130 wheel) дала GPU-ускорение для RTX 5070 Ti
(Blackwell, sm_120). Совокупный прирост скорости: ×3.2 на полный прогон.

Подробности миграции — в CHANGELOG, v15.14.

### Q: Почему именно cu130 (CUDA 13.0)?

**A**: Соответствие системному CUDA Toolkit 13.x. Раньше использовали cu128
(CUDA 12.8), что работало нормально, но смешение версий — потенциальный
источник проблем при компиляции custom extensions.

Прирост производительности от cu128 → cu130 нулевой для нашей нагрузки
(LSTM на FP32). Это «косметическое» обновление для чистоты окружения.

### Q: Почему GPU нужен только для LSTM, а не для XGBoost?

**A**: XGBoost тоже использует GPU (`tree_method='hist', device='cuda'`),
но для нашего размера данных (~3000 строк × 43 фичей) разница CPU vs GPU
у XGBoost минимальная. У LSTM наоборот — GPU критичен из-за рекуррентной
природы и большого числа параметров (~155k).

## История разработки v16 (отвергнутые гипотезы)

### v16.0 — log-returns target

**Гипотеза**: log-returns scale-invariant, должны решить проблему
экстраполяции тренда LSTM на длинных горизонтах.

**Результат**: LSTM получает нулевой вес, Direction Accuracy 0%.

**Корень**: MSE на низковариативном таргете → Optuna выбирает
«predict mean» как оптимум.

→ **Откачено** в v16-B2.

### v16-B2 — оставлены только relative features

**Что осталось**: 4 relative features, PyTorch cu130, метрики Naive/IC/R²-on-returns.

**Что отброшено**: log-returns, StandardScaler, расширенный LSTM (15 фич).

→ **Закоммичено**.

### v16-B1 — correlation scorer для Ridge

**Гипотеза**: directional scoring оживит LSTM в Ridge.

**Результат**: LSTM ожил (вес 0.371), но Model Error вырос до 8.57% —
Ridge сжимается к среднему.

→ **Отвергнуто**, переход к B1.1 с R² scoring.

### v16-B1.1 — R² scoring для Ridge

**Гипотеза**: R² штрафует и за ошибку, и за слабую корреляцию — баланс
между MSE и correlation.

**Результат**: LSTM ожил на 3/5 дат (вес 0.005-0.204), Avg Error
1.30 → 1.27%, Direction Accuracy сохранён (67%).

→ **Закоммичено**, текущее состояние ветки `log-returns-v16`.

### v16-D — log-returns + R² scoring (повторная попытка)

**Гипотеза**: R² scoring мог исправить проблему v16.0, log-returns
дополнительно решат экстремальные тикеры (PLZL).

**Результат смешанный**:

- PLZL: Error 32.27% → 1.59% (победа, но через lucky bias)
- SBER/LKOH/GAZP: Direction 100/100/67% → 0/0/0% (катастрофа)

→ **Откачено**. Log-returns не universal solution даже с R² scoring.
